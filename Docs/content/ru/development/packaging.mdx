# Упаковка и релизы

`Packaging/` содержит поддерживаемые точки входа релизной сборки. Каждый сценарий создает пакеты из одного автономного publish с Hyprism Launcher и отдельным apphost Local Node

Проект Desktop сохраняет `Hyprism.Desktop` как assembly identity для URI ресурсов Avalonia. Обычные `dotnet build`, `dotnet run` и `dotnet publish` используют стандартное имя apphost от SDK: `Hyprism.Desktop` (`Hyprism.Desktop.exe` в Windows)

Платформенные сценарии переименовывают опубликованный native apphost в `Hyprism Launcher` (`Hyprism Launcher.exe` в Windows) перед подписью или созданием пакетов. Nix flake предоставляет лаунчер под этим именем после создания обёрток исполняемых файлов. Эти шаги упаковки сохраняют managed assembly и пути встроенных ресурсов

## Целевые платформы

| Хост | Runtime | Цели |
| --- | --- | --- |
| Linux | `linux-x64` | `deb`, `rpm`, `appimage`, `flatpak`, `tar`, `nix` |
| Windows | `win-x64` | `zip`, `msi`, `exe` |
| macOS | `osx-arm64` | `dmg` |

Собирайте пакеты на соответствующей платформе. Нативные упаковщики принимают `all` и `--output`, стандартный каталог результата: `dist`

## Linux

Установите инструменты выбранных форматов: `dpkg-deb`, `rpmbuild`, `appimagetool`, `flatpak` и `flatpak-builder`

```bash
./Packaging/publish-linux.sh deb rpm tar --output dist
./Packaging/publish-linux.sh all --output dist
```

Цель `all` создает DEB, RPM, AppImage, Flatpak и tar.xz. Цель Nix запускается отдельно, потому что пакет предоставляется flake и сохраняется в `/nix/store`

Инструмент AppImage можно задать через `--appimagetool` или `APPIMAGETOOL`. Экспорт Flatpak и bundle используют ветку `stable`

Flatpak сейчас использует бэкенд Avalonia X11 через XWayland, поэтому его манифест выдаёт `--socket=x11` и не выдаёт условный `fallback-x11` или нативный сокет `wayland`. Это позволяет запускать KDE Plasma Wayland до включения нативного Wayland в настольном хосте

Linux-пакеты сохраняют исходный рисунок из `logo.svg` и публикуют его в квадратном SVG viewport, который требуется валидаторам иконок приложений

## Nix

Репозиторий содержит flake для нативного пакета `x86_64-linux`. Установите Nix с поддержкой flakes, затем собирайте или запускайте Hyprism из корня репозитория или тега релиза

```bash
nix build ./Packaging/linux/flake#hyprism
nix run ./Packaging/linux/flake#hyprism
./Packaging/publish-linux.sh nix
```

Flake закрепляет nixpkgs и восстанавливает NuGet-зависимости из `Packaging/linux/flake/nix/deps.json`. Обновляйте этот файл при изменении ссылок на .NET-пакеты

Пакет предоставляет стабильную команду `hyprism` и включает executable `Hyprism Launcher` и отдельный executable `Hyprism.LocalNode` в результате

Nix сохраняет результат в `/nix/store`, параметр `--output` относится только к нативным пакетам

Чтобы пересоздать lockfile NuGet-зависимостей, соберите служебный скрипт пакета и запустите его с путем к lockfile

```bash
nix build ./Packaging/linux/flake#hyprism.fetch-deps
./result ./Packaging/linux/flake/nix/deps.json
```

## Windows

Для MSI и EXE сценарий устанавливает закрепленную версию WiX во временный каталог

```powershell
pwsh Packaging/publish-windows.ps1 all --output dist
```

Перед созданием пакетов проверяется наличие `Hyprism Launcher.exe` и отдельного `Hyprism.LocalNode.exe`. ZIP содержит те же файлы приложения, что и установщики

Windows apphost использует многомасштабный ресурс `Sources/Hyprism.Desktop/Assets/Images/Hyprism.ico`. WiX использует ту же иконку для записи MSI в списке приложений и для EXE-bootstrapper

## macOS

В app bundle macOS входит сгенерированная из `logo.svg` иконка `Packaging/macos/Hyprism.icns`, а executable и отображаемое имя используют `Hyprism Launcher`. Сценарий macOS использует `plutil`, `hdiutil`, `codesign` и `file`

```bash
./Packaging/publish-macos.sh dmg --output dist
```

Он создает app bundle для Apple Silicon, проверяет архитектуры apphost Hyprism Launcher и Local Node, применяет и проверяет ad hoc подпись, затем создает DMG. Такая подпись не является нотарификацией

## Источник версии

Версия релиза задается в `Version` файла `Sources/Hyprism.Desktop/Hyprism.Desktop.csproj`. Сценарии получают ее через MSBuild

```bash
dotnet msbuild Sources/Hyprism.Desktop/Hyprism.Desktop.csproj \
  -nologo -getProperty:Version
```

Релизный тег должен совпадать с `v<Version>`. При несовпадении workflow останавливается до упаковки

## Ответственность CI

| Workflow | Назначение |
| --- | --- |
| `ci.yml` | Группы проверок Core, Desktop, Local Node и Packaging |
| `test-core.yml`, `test-desktop.yml`, `test-local-node.yml` | Отдельные матрицы Ubuntu, Windows и macOS |
| `build.yml` | Выбор платформ |
| `build-linux.yml`, `build-windows.yml`, `build-macos.yml` | Зависимости платформ, проверка Nix и вызов упаковщиков |
| `release.yml` | Проверка версии, общие сборки пакетов, релизные файлы |
| `docs-pages.yml` | Проверка документации и GitHub Pages |
| `reuse.yml` | Лицензионные заголовки и REUSE |

Отдельный workflow Flathub и `Scripts/update-flathub-manifest.sh` содержат старые пути Electron/frontend. Они не являются поддерживаемым входом нативной упаковки и требуют миграции перед использованием

Linux workflow создает нативные Linux-пакеты и в том же job запускает `nix flake check --print-build-logs` для Nix-пакета. В `ci.yml` группа Packaging ожидает завершения workflow тестов Core, Desktop и Local Node
