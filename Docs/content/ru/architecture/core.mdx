# Hyprism.Core

Core содержит поведение лаунчера, которое работает без UI-фреймворка. Интерфейсы расположены рядом с реализациями, а возможности хоста находятся в `Application/Ports`

## Подсистемы

| Каталог | Ответственность |
| --- | --- |
| `Application/Composition` | Регистрация зависимостей и асинхронная инициализация |
| `Application/Progress` | Прогресс, стадии, завершение и ошибки операций экземпляра |
| `Application/Ports` | Предоставляемые хостом Discord presence и обнаружение GPU |
| `Accounts/Authentication` | Официальный OAuth, обновление сессии, хранение токенов, страница callback |
| `Accounts/Profiles` | Выбор личности, профили, порядок, миграции, игровое время |
| `Accounts/Identity` и `Accounts/Skins` | Личность профиля и данные персонажа |
| `Game/Versions` и `Game/Sources` | Каталоги версий, официальный источник, обнаружение и выбор зеркал |
| `Game/Download` и `Game/Patching` | Возобновляемые загрузки, дифференциальные обновления, Butler |
| `Game/Instances` | Реестр, пути, импорт, метаданные, удаление и миграции экземпляров |
| `Game/Launch` | Java, аутентификация, патчи клиента, параметры JVM и GPU, процессы |
| `Game/Mods` | API CurseForge и Modifold, совместимость, импорт, включение и обновления |
| `Game/Assets` | Поиск и резервное хранение аватаров |
| `Infrastructure` | JSON, каталоги приложения, кэш, логи, HTTP-идентификация |
| `Integrations/Hytale` | Заголовки протокола официального лаунчера |

## Координация операций

`GameLaunchCoordinator` проверяет запуск установленного экземпляра. `GameInstallationWorkflow` работает с выбранными веткой и числовой версией при установке или явном обновлении, а после подготовки вызывает `GameLauncher`. Порядок и отмена описаны в [жизненном цикле игры](/architecture/game-lifecycle)

Репозитории публикуют `InstancesChanged` и `ProfilesChanged` после изменений. Потребители подписываются на события вместо опроса диска или предположения, что данные меняют только они

## Граница хоста

Core принимает callback `AuthUriPresenter` для интерактивного OAuth. Хост открывает браузер и может предоставить `IOAuthCallbackPageRenderer` для ответа локального обработчика

Core определяет пути профилей и экземпляров, а Desktop открывает их папки. Выбор GPU использует `IGpuProvider`, presence использует `IDiscordPresence`, автономный запуск использует `ILocalNodeServiceFactory`

Разбор новостей и метаданные GitHub принадлежат Desktop, поскольку обслуживают представление, а не правила игры или аккаунтов

## Хранение и совместимость модов

`ModManager` хранит файлы в `UserData/Mods` целевого экземпляра. Отключение добавляет суффикс `.disabled`, включение возвращает обычное имя. Метаданные связывают установленный файл с идентификаторами проекта и файла его источника. Для Modifold в манифесте экземпляра сохраняются источник, идентификатор проекта и адрес публичной страницы.

Связи CurseForge нормализуются и сохраняются в манифесте экземпляра. Необходимые связи разрешаются графом в глубину до установки, циклы и неразрешенные обязательные узлы завершают операцию ошибкой, необязательные связи сохраняются, но автоматически не устанавливаются, а несовместимые связи проверяются по текущему набору установленных модов. JAR- и ZIP-архивы также проверяются на наличие корневого `manifest.json`; его идентификатор плагина, версия и диапазоны зависимостей сохраняются для проверки и защиты от удаления

`ModCompatibilityEvaluator` читает установленную версию сервера и сравнивает ее с версиями игры в каталоге. UI запрещает установку несовместимых файлов, а неизвестная версия остается отдельным состоянием

Примеры интеграции приведены в [контрактах Core](/reference/services), правила хранения в [данных и кэше](/architecture/data-and-cache)
